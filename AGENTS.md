# AGENTS.md

Operating notes for AI/agent sessions working in this repo. Read first.

## Hard rules

1. **Never write Blizzard credentials to a file that gets committed.** Locally they live only in `.env` (gitignored); in CI they live only in the repo's encrypted GitHub Actions secrets (`BLIZZARD_CLIENT_ID` / `BLIZZARD_CLIENT_SECRET`).
2. **Never hardcode the expansion, patch, or season ID anywhere.** They must come from `discover.mjs` at scraper boot. If you see a hardcoded `12.1.0`, `midnight`, or `18` in `scripts/`, it's a bug. (The period `1078` is the most recently discovered value; treat it as an example, not a constant.)
3. **Never hand-edit `data/aggregated_bis.json`.** It is generated by `scripts/run-once.mjs`. Bulk corrections to existing data go through the committed one-off scripts (see File touch map) which validate against the schema before writing.
4. **`scripts/verify-credentials.mjs` must remain token-only.** No scraping, no `aggregated_bis.json` write, no spec fetch. If you find yourself wanting to "just fetch one profile" in the verifier, create a new script instead.
5. **Data sources are two-tier.** Candidate discovery comes from Raider.IO's per-spec rankings endpoint (`scripts/lib/raiderio.mjs`); gear, talents, items, and item media come from the official Blizzard Game Data API. Don't swap one for the other.
6. **No "Yes-Man" syndrome / Brutal honesty.** Never just agree or rubber-stamp ideas. If an approach, architecture, or code change is flawed, fragile, or overcomplicated, state it plainly and suggest a better way. Challenge assumptions and ask questions—even against the user's suggestions—whenever confidence is not high.
7. **Rigorous verification over assumptions.** Re-check all work, tests, and data against actual schemas and live outputs. Do not guess or claim high confidence without validating first.
8. **Security first always.** Strict zero-leak policy for secrets, tokens, and API credentials. Never loosen permissions or expose sensitive environment variables.
9. **Frugal / zero-cost preference ("Cheapskate" standard).** Always prefer 100% free and open-source tools, free-tier APIs, serverless static hosting (GitHub Pages), and GitHub Actions free runner minutes. Never introduce paid tooling, paid APIs, or cloud costs when a free or local alternative exists.
10. **Zero-destructive deletion policy.** Never delete files, directories, branches, or data unless 1000% certain there is zero adverse impact, or an explicit backup is created first. When in doubt, ask or archive.

## Multi-agent protocol (all agents: Claude Code, opencode, agy/AntiGravity, future ones)

This repo is worked on by **multiple AI agents** (and the human, Gideon). Coordination is file-based so it works across every tool. **Hard rules 1–10 above bind every agent equally.**

**Commit attribution — mandatory prefixes.** Start every commit message with your prefix:

- `[claude]` — Claude Code sessions
- `[opencode]` — opencode sessions

- `[gideon]` — Gideon's own manual commits

If you find another agent's *uncommitted* work in the tree, commit it **separately** with *their* prefix and a note ("committed by opencode on behalf of agy") before starting your own work — never mix another agent's changes into your commit.

Rules:
- **Exempt from locking:** `PROGRESS.md` (edit only your own lock rows; append to the log) and `CHANGELOG.md` (add lines under `[Unreleased]`).
- **Touching a file outside your areas** (e.g. a Home feature needs `components.css`): claim that area too, or stop and ask Gideon. Never edit it unclaimed.
- **`shared-ui` cache-busters:** whoever holds `shared-ui` may bump `?v=` query strings in any page's HTML without holding that page's area — nothing else in those files.
- **New files** belong to the area of the feature they serve; if unclear, ask. New areas are added to this table under the `repo` lock.
- **Stale locks:** a lock older than 48h with no matching commits may be flagged to Gideon. Never take over another agent's lock yourself.

**Session loop — follow in order:**

1. `git pull` — never start on a stale tree (CI bot commits data 2× daily, 09:00 & 21:00 UTC)
2. Read `PROGRESS.md` → **Current locks**. If an area you need is held by another agent: **don't edit its files** — pick other work or wait
3. Claim: set your area row(s) (owner, task, UTC time, branch), commit `[<prefix>] lock: <area> — <task>`, push to `main` immediately. If the push is rejected, `git pull`, re-check the row is still free, and retry
4. Do the work (directly on `main`, or on a branch — see below)
5. Add a `CHANGELOG.md` line for user-visible changes (see Versioning)
6. Commit `[<prefix>] <type>: <description>`, push
7. When the work is on `main`: append a timestamped PROGRESS.md log entry (what you did, files touched, next step) and reset your row(s) to `—` / OPEN in the same commit
8. Never end a session with uncommitted changes; never force-push; never rebase shared history

**Branches and pull requests.** opencode and agy may commit straight to `main`. **Claude works on branches**: `claude/<area>-<short-topic>`, then opens a **draft pull request** to `main`. Gideon merges; Claude never merges its own PRs. The lock row stays claimed (with the branch name) until the PR is merged or closed, then Claude logs and releases it on `main`. Locks and log entries are always committed directly to `main`, never only on a branch, so other agents can see them.

**Never run two scrapers at once** (Blizzard throttles hard after ~736 leaderboard calls — parallel runs cause 403 storms). Running any scraper or data-repair script requires the `data-pipeline` lock. Cloud agents (e.g. Claude Code Project threads) never run the scraper — CI does that.

**Per-agent workspaces.** Each agent works in its own local clone; **git (origin/main) is the only sync boundary** — never reach into another agent's clone, never share a working tree:

- claude (Claude Code): `C:\Users\Gideon\OneDrive\AI\Claude Code\Projects\Metagor\Main` locally; Claude Code Project threads run in cloud sandboxes that clone `origin` (same `[claude]` prefix and rules)
- opencode: `C:\Users\Gideon\OneDrive\AI\OpenCode\Projects\Meta'gor`
- agy (AntiGravity): `C:\Users\Gideon\OneDrive\AI\AntiGravity\Projects\metagor`

Rules: `git pull` before every session and before every commit; push immediately after committing so the other agents see your work; if the same file conflicts, the lock protocol (not a merge battle) decides who edits.

**OneDrive note:** all three clones live in OneDrive. Two agents writing simultaneously can hit transient file locks — if you see bizarre write failures, stop and tell Gideon rather than retrying blindly.

## Versioning & changelog (all agents)

- **Semantic versioning** (`MAJOR.MINOR.PATCH`). Stay on `0.x` until production (Cloudflare + custom domain). New feature → MINOR, fix-only → PATCH.
- **`CHANGELOG.md`** uses [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Every user-visible change adds a line under `## [Unreleased]` (Added / Changed / Fixed / Removed / Security) **in the same commit as the change**. Skip bot data refreshes and lock/log-only commits.
- **Releases only when Gideon says so.** Then: move Unreleased under `## [X.Y.Z] - YYYY-MM-DD`, update the compare links at the bottom, bump `package.json` `version`, commit `[<prefix>] release: vX.Y.Z`, tag `vX.Y.Z` (annotated), push the tag, and create a GitHub Release (`gh release create vX.Y.Z`) with that version's changelog section as notes. Never tag, re-tag, or delete tags on your own initiative.

## Data refresh automation (primary path)

`.github/workflows/scrape.yml` runs the full scrape **twice daily (09:00 & 21:00 UTC)** on GitHub Actions, commits fresh data as `github-actions[bot]`, and the push auto-triggers the Pages deploy. Your PC is not in the loop.

```
# Manual trigger from a terminal
gh workflow run scrape.yml --repo gitgipie/metagor

# Watch the latest run
gh run list --repo gitgipie/metagor --workflow scrape.yml --limit 1
```

- CI credentials come from repo secrets — set via `gh secret set BLIZZARD_CLIENT_ID/SECRET`.
- Cold-cache full runs take **2–3 hours** (workflow timeout is 4h). Don't lower it.
- Local runs still work identically (`node scripts/run-once.mjs`); CI just makes them unnecessary.

## Spec ID convention

Always `<class-slug>-<spec-slug>`, e.g. `demon-hunter-havoc`, `mage-arcane`. Used as the key in both `aggregated_bis.json` and `guides.json`. Cross-reference: `scripts/lib/config.mjs` SPECS array has both our slug and Blizzard's `blizzardClassId` / `blizzardSpecId` for each.

## Slot names

The 16 equipment slots: `head neck shoulders back chest wrists hands waist legs feet finger1 finger2 trinket1 trinket2 mainhand offhand`. The renderer maps to display labels; the data file uses these keys.

## Operational notes

**Blizzard throttling.** After ~736 leaderboard calls in a single script invocation, Blizzard's profile API starts returning 403 for several minutes. Mitigations: 12h leaderboard disk cache, 3s pause after the leaderboard batch, sequential profile fetches with 400ms spacing. Many `403`s in a run = real throttle; wait 5-10 minutes and re-run — the cache means the next run skips the leaderboard batch entirely. On CI this manifests as a failed workflow run; the next cron slot retries.

**Stale journal loot lists.** Blizzard's journal-instance loot tables lag new raid tiers by days. If raid items show bare `Raid` without a raid name / BOSS line, delete `data/cache/blizzard_item-to-raid-map.json` and run `node scripts/re-enrich-sources.mjs` (rebuilds the map + re-enriches the data).

**Crest/upgrade tracks.** `public/js/render/gear.js` has no rank display anymore (removed for consistency); item source labels are deliberately bracket-free (`Raid · <Name>`, `Mythic+ · Tier` — never `Raid (Heroic)`, never `Mythic+ (Catalyst)`). Keep it that way: the source tag must not claim origins Blizzard's data can't prove.

## Deploy

`deploy-pages.yml` deploys to **GitHub Pages** on every push to `main` (stages `public/*` + `data/aggregated_bis.json` + `data/guides.json` into `_site`). No build step. Live at `https://gitgipie.github.io/metagor/`. Fresh data reaches the site via the scheduled scrape's bot commit, or any manual push.
